    A CoRIM Profile for Arm's Normal World Attestation Endorsements
                  draft-yd-nw-rats-endorsements-latest

Abstract

   Arm Normal World Attestation Endorsements comprise reference values
   and cryptographic key material that a Verifier needs to appraise
   Attestation Evidence produced from Normal World client running on an
   Arm Platform.

   This memo defines Normal World Endorsements as a profile of the CoRIM
   data model.

1.  Introduction

   Arm's Normal World Remote Attestation provides a mechanism for a
   Normal World client to obtain a Remote Attestation token from the
   underlying Arm platform.

   Arm's Normal World Endorsements comprise of reference values and
   cryptographic key material that an Attestation Verifier requires.
   These Endorsements are used to appraise Attestation Evidence produced
   by a Normal World client running on an Arm platform.

   This memo defines Normal World Endorsements as a profile of the CoRIM
   data model [I-D.ietf-rats-corim].

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",

   capitals, as shown here.

   The reader is assumed to be familiar with the terms and concepts
   introduced in Section 4 of [RFC9334].

3.  Arm NW Endorsements

   Arm's Normal World Endorsements comprise of Arm Platform
   Endorsements.

   Appraising Arm Normal World Evidence requires Endorsements for the
   Arm Platform.  This document outlines the Platform in Section 3.1.

   It also provides the Evidence transformation logic for conducting
   appraisals using the CoRIM processor (see Section 8 of
   [I-D.ietf-rats-corim]) for platform claim sets.

3.1.  Arm Platform Endorsements

   There are two types of Arm Platform Endorsements:

   *  Reference Values (Section 3.1.3), i.e., measurements of the Arm
      Platform firmware.

   *  Attestation Verification Keys (Section 3.1.4), i.e., cryptographic
      keys that can be used to verify Evidence produced by the Arm
      Platform, along with the identifiers that link the keys to their
      platform instances.

3.1.1.  Arm Platform Endorsement Profile

   Arm Platform Endorsements are carried in one or more CoMIDs within a
   CoRIM.

   The profile attribute in the CoRIM MUST be present and MUST be the
   URI tag:arm.com,2026:endorsements/arm_nw_platform#1.0.0, as shown in
   Figure 1.

   / corim-map / {
     / corim.profile / 3:
       32("tag:arm.com,2026:endorsements/arm_nw_platform#1.0.0")
     / ... /
   }

           Figure 1: CoRIM profile for Arm Normal World Platform
                         Endorsements version 1.0.0

3.1.2.  Arm Platform Endorsements linkage to Arm Platform

   Each Arm Platform Endorsement, be it a Reference Value or an
   Attestation Verification Key, is associated with a unique identifier
   known as Arm Platform Implementation ID.  The Implementation ID
   uniquely identifies a given implementation of a Arm Platform and it
   is used by the Endorser or Reference Value Provider as an anchor to
   which Reference Values and Attestation Verification Keys for a Arm
   Normal World Platform are linked.

   To encode an Implementation ID, the tagged-bytes variant of the
   $class-id-type-choice is used, as described in Figure 2.  The length
   of the byte string MUST be exactly 32.

   impl-id-tagged-bytes = #6.560(arm-platform-implementation-id-type)

   arm-platform-implementation-id-type = bytes .size 32

             Figure 2: Arm Platform Implementation ID encoding

   Besides, a Arm Platform Endorsement can be associated with a specific
   _instance_ of a certain Arm Platform implementation - as is the case
   of Attestation Verification Keys.  The Instance ID provides a unique
   identifier for a given Arm Platform instance.

   To encode an Instance ID, the tagged-ueid-type variant of the
   $instance-id-type-choice is used, as described in Figure 3.  The
   first byte MUST be 0x01 (RAND) followed by the 32-byte unique
   instance identifier.

   inst-id-tagged-ueid = #6.550(eat-ueid-rand-type)

   eat-ueid-rand-type = bytes .join eat-ueid-rand-fmt

   eat-ueid-rand-fmt = [
     ; the type byte is 0x01
     ueid-rand-typ
     bytes .size 32
   ]

   ueid-rand-typ = h'01'

                Figure 3: Arm Platform Instance ID encoding

   Arm Attestation Verification Keys are associated with an Arm Platform
   instance by means of the Instance ID and the corresponding
   Implementation ID.  These identifiers are typically found in the
   subject of a CoMID triple, encoded in an environment-map as shown in
   Figure 4.

   / environment-map / {
     / comid.class / 0 : {
       / comid.class-id (implementation id) / 0 :
         / tagged-bytes / 560(
           h'61636d652d696d706c656d656e746174
             696f6e2d69642d303030303030303031'
         )
     },
     / comid.instance / 1 :
       / tagged-ueid-type (instance id) / 550(
         h'01
           4ca3e4f50bf248c39787020d68ffd05c
           88767751bf2645ca923f57a98becd296'
       )
   }

               Figure 4: Example Arm Platform Identification

   Together, they are interpreted as a unique identifier of the Arm
   Platform.

3.1.3.  Reference Values

   Reference Values carry measurements and other metadata associated
   with the updatable firmware of the Arm Platform.

   When appraising Evidence, the Verifier compares Reference Values
   against:

   *  The values found in the Software Components of the Arm Normal
      World Platform token.

   *  The value set in the platform configuration of the Arm Normal
      World Platform token.

   Each measurement is encoded in a measurement-map of a CoMID
   reference-triple-record.  Since a measurement-map can encode one or
   more measurements, a single reference-triple-record can carry as many
   measurements as needed, provided they belong to the same Arm Platform
   identified in the subject of the triple.  A single reference-triple-
   record MUST completely describe the Arm Platform measurements.

3.1.3.1.  Arm Platform Software Components

   Each Arm Platform software component is encoded in a measurement-
   values-map as defined in Figure 5.

   arm-swcomp-measurement-values-map = {
     ? &(version: 0) => arm-swcomp-version-map
     &(digests: 2) => arm-swcomp-digests-type
     ? &(name: 11) => arm-swcomp-name
     &(cryptokeys: 13) => [ arm-swcomp-signer-id ]
   }

   arm-swcomp-version-map = {
     &(version: 0) => text
   }

   arm-swcomp-digests-type = [ + arm-digest ]

   arm-digest = [
     alg: text
     val: arm-hash-type
   ]

   arm-hash-type = bytes .size 32 / bytes .size 48 / bytes .size 64

   arm-swcomp-name = text

   arm-swcomp-signer-id = #6.560(arm-hash-type)

             Figure 5: ARM Platform Software Component encoding

   version (key 0):
      A version-map with its version field containing the version (key
      4) of the arm-platform-sw-component.  The version-scheme field of
      the version-map MUST NOT be present.  This field is optional.

   digests (key 2):
      Each array element encodes the "measurement value" (key 2) and
      "hash algorithm identifier" (key 6) of the arm-platform-sw-
      component in the val and alg entries, respectively.  The alg entry
      MUST use the text encoding.  The digests array MUST contain at
      least one entry and MAY contain more than one entry if multiple
      digests (obtained with different hash algorithms) of the same
      measured component exist.  If multiple entries exist, they MUST
      have different alg values.  This field is mandatory.

   name (key 11):
      A text value containing the "component type" (key 1) of the arm-
      platform-sw-component.  This field is optional.

   cryptokeys (key 13):
      An array with _only one_ entry using the tagged-bytes variant of
      the $crypto-key-type-choice.  The entry contains the "signer id"
      (key 5) of the arm-platform-sw-component.  This field is
      mandatory.

   Each measurement-values-map for a ARM Platform software component is
   wrapped in a measurement-map with an mkey using the text variant of
   the $measured-element-type-choice.  The value of the mkey MUST be
   "arm.platform.software-component".  The authorized-by field of the
   measurement-map MUST NOT be present.  Find the related CDDL
   definitions in Figure 6.

   arm-swcomp-measurement-map = {
     &(mkey: 0) => "arm.platform.software-component"
     &(mval: 1) => arm-swcomp-measurement-values-map
   }

         Figure 6: ARM Platform Software Component measurement-map

3.1.3.2.  ARM Platform Configuration

   The ARM Platform configuration describes the set of chosen
   implementation options of the ARM Platform.  For example, this may
   include a description of the level of physical memory protection
   provided.

   ARM Platform configuration is vendor-specific variable-length data.
   Only some of the data may be security-relevant.  For these reasons,
   it is represented in a raw-value of the measurement-values-map, using
   the tagged-masked-raw-value variant of the $raw-values-type-choice.
   Refer to Section 5.1.4.1.4.6 of [I-D.ietf-rats-corim] for the details
   about the comparison algorithm.

   arm-config-measurement-values-map = {
     &(raw-value: 4) => arm-tagged-masked-raw-value
   }

   arm-config-tagged-masked-raw-value = #6.563([
     value: bytes
     mask: bytes
   ])

        Figure 7: ARM Platform Configuration measurement-values-map

   The measurement-values-map for a ARM Platform configuration is
   wrapped in a measurement-map with an mkey using the text variant of
   the $measured-element-type-choice.  The value of the mkey MUST be
   "arm.platform.platform-config".  There MUST be only one measurement-
   map with mkey "arm.platform.platform-config" in the triple.

   The authorized-by field of the measurement-map MUST NOT be present.
   Find the related CDDL definitions in Figure 8.

   arm-config-measurement-map = {
     &(mkey: 0) => "arm.platform.platform-config"
     &(mval: 1) => arm-config-measurement-values-map
   }

            Figure 8: ARM Platform Configuration measurement-map

3.1.3.3.  Arm Platform Trusted Board Boot ROTPK

   When an implementation of the Arm Platform follows the Trusted Board
   Boot [TBB] specification, the platform will include several
   provisioned public key identifiers to establish a chain of trust.
   Each public key identifier is expressed as a hash of the
   corresponding public key.

   For Arm platform Implementation, the public key identifiers are
   provisioned as a number of array entries, with each array entry
   containing a list of key identifiers.

   For Arm platform Implementation, there MUST be only two types of
   arrays, corresponding to the provisioning lifecycle stage:

   1.  Chip Manufacturing array - known as "CM"

   2.  Device Manufacturing array - known as "DM"

   In Arm platform Implementation, for a particular type of array, the
   maximum number of array entries SHALL be 8, while the maximum entries
   in a single array SHALL be 6.

   Arm Platform public key identifiers are encoded in a CoMID using
   Reference Value triples.

   Each array entry is encoded in a single Reference Value Triple.

   Each public key identifier is encoded in a single measurement-map.

   1.  mkey uniquely identifies the position of each key identifier,
       using the text variant of $measured-element-type-choice.  The
       encoding follows a consistent pattern: the prefix
       "arm.platform.rotpk", followed by the set name ("CM" or "DM"),
       and finally the entry position within the active array (starting
       from zero).  The parts are separated by ".". mkey is aligned to
       the elements received in the TBB RoTPK claim from the Arm
       Platform evidence.

   For example, to encode a "CM" key identifier at active position 3,
   mkey will be set to "arm.platform.rotpk.CM.3".

   1.  The public key identifier is encoded using cryptokeys (key 13).
       The array MUST have only one entry encoded using the tagged-bytes
       variant of the $crypto-key-type-choice.  The length of the
       tagged-bytes MUST be 32, 48 or 64 bytes.

   2.  The authorized-by field of the measurement-map MUST NOT be
       present.

   Find the related CDDL definition of Measurement Values Map in
   Figure 9 and the associated measurement map in Figure 10.

   arm-rotpk-measurement-values-map = {
     &(cryptokeys: 13) => [ arm-rotpk-id ]
   }

   arm-hash-type = bytes .size 32 / bytes .size 48 / bytes .size 64

   arm-rotpk-id = #6.560(arm-hash-type)

            Figure 9: Arm Platform ROTPK measurement-values-map

   arm-rotpk-measurement-map = {
     &(mkey: 0) => text .regexp "arm.platform.rotpk.[CD]M\\.[0-5]"
     &(mval: 1) => arm-rotpk-measurement-values-map
   }

               Figure 10: Arm Platform ROTPK measurement-map

   An Endorser may choose to provision either the entire set of entries
   or the single active entry currently in use on the platform.

3.1.3.4.  Arm Platform Manufacturing Configuration

   The Arm Platform Manufacturing Configuration represents a record of
   production phases and testing conducted during the manufacturing
   process for the platform instance.

   Arm Platform Manufacturing Configuration is vendor-specific variable-
   length data.

   It is represented in a raw-value of the measurement-values-map, using
   the tagged-masked-raw-value variant of the $raw-values-type-choice.
   Refer to Section 5.1.4.1.4.6 of [I-D.ietf-rats-corim] for the details
   about the comparison algorithm.

   arm-manufacturing-config-measurement-values-map = {
     &(raw-value: 4) => arm-tagged-masked-raw-value
   }

   arm-config-tagged-masked-raw-value = #6.563([
     value: bytes
     mask: bytes
   ])

      Figure 11: Arm Platform Manufacturing Configuration measurement-
                                 values-map

   The measurement-values-map for an Arm Platform manufacturing
   configuration is wrapped in a measurement-map with an mkey using the
   text variant of the $measured-element-type-choice.  The value of the
   mkey MUST be "arm.platform.platform-manufacturing-config".  There
   MUST be only one measurement-map with mkey "arm.platform.platform-
   manufacturing-config" in the triple.

   The authorized-by field of the measurement-map MUST NOT be present.

   Find the related CDDL definitions in Figure 11 and in Figure 12.

   arm-config-measurement-map = {
     &(mkey: 0) => "arm.platform.platform-manufacturing-config"
     &(mval: 1) => arm-manufacturing-config-measurement-values-map
   }

    Figure 12: Arm Platform Manufacturing Configuration measurement-map

3.1.4.  Attestation Verification Keys

   An Attestation Verification Key contains the public key associated
   with the Arm Platform Attestation Key (CPAK).  When appraising
   Platform Evidence, the Verifier uses the Implementation ID and
   Instance ID claims found in the Platform Token to identify the key
   that it shall use to verify the signature on the Arm Platform token.
   This allows the Verifier to prove (or disprove) the Attester's
   claimed identity.

   Each verification key is provided with the corresponding Arm Platform
   Instance and Implementation IDs in an attest-key-triple-record.
   Specifically:

   *  The Instance and Implementation IDs are encoded in the
      environment-map as described in Section 3.1.2;

   *  The CPAK public key uses the tagged-pkix-base64-key-type variant
      of the $crypto-key-type-choice.

   The CPAK public key is a SubjectPublicKeyInfo [RFC5280] using the
   encoding defined in Section 13 of [RFC7468].  There MUST be only one
   key in an attest-key-triple-record.
